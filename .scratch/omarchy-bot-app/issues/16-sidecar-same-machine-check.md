# 16: Sidecar decides "same machine" by host identity, not by loopback address

**What to build:** The app decides whether to start the Local Sidecar by asking whether the paired Service runs on this machine, not by whether its address is loopback. A user who reaches a remote Service through an SSH tunnel to `localhost` gets the Sidecar and can approve `local.run`, file and search actions on their own computer (stories 21, 32–34). A user whose Service really is on the same machine gets no Sidecar, whether they connect through loopback or through a LAN/HTTPS address. This restores the spec line "the existing same-host check is unchanged" and ADRs 0011/0015 ("only when it is not connected to the plugin daemon on the same machine").

Recommended mechanism (the agent may choose another if it records why): the Service exposes a non-secret host identity to Paired Devices, for example a per-install random salt plus a digest of that salt and the host's machine ID. The app computes the same digest from its own machine ID and compares. A different machine cannot recover the machine ID from the digest. On macOS and Windows the comparison is always "different machine". If the check cannot be completed, the app starts no Sidecar and shows that local actions are unavailable and why. It never guesses "off-host".

**Blocked by:** None (can start immediately)

**Status:** resolved

## Comments

Resolved after independent review. The app now compares an authenticated salted host-identity digest and starts the Sidecar only when the Service is on a different machine; loopback is no longer the detector, and a failed check starts nothing and shows a recoverable notice. Implementation uses the recommended authenticated salted machine identity. `GET /api/host-identity` requires a Paired Device token and returns only `{salt,digest}`: a persisted 32-byte lowercase hex salt at `stateDir/host-identity-salt` (mode 0600) and SHA-256 of `${salt}:${trimmedMachineId}`. Linux reads `/etc/machine-id`, then `/var/lib/dbus/machine-id`; an explicit `OMARCHY_BOT_MACHINE_ID_FILE` overrides both on the Service and app for isolated fixtures. Missing, empty, unreadable or invalid identity material fails closed. The app fetches with its paired token, refuses redirects, bounds the request to ten seconds, validates the response, and asks native Rust to hash its machine ID. Only a different digest starts the bundled Sidecar. Raw machine IDs never enter the API response or renderer. macOS and Windows skip comparison because neither can host the Service.

The decision lives in the existing native shell adapter so the confirmed shell seam exercises startup and recovery without a second HTTP stack in Rust. Native setup no longer starts the Sidecar eagerly; its existing process, stdio, approval and teardown boundary remains unchanged. Identity failure shows an alert explaining local actions are unavailable and instructing the user to fix the connection and reopen the app. There is no automatic retry. The shared WebSocket URL conversion now supplies both CSP and Sidecar startup, and the device-id test uses “Web UI”.
