# 10: Windows executor for the Sidecar

**What to build:** On Windows the Local Sidecar runs commands with Windows PowerShell 5.1, each job assigned to a Job Object closed with kill-on-close on cancel or timeout, and refuses Windows credential and key stores in AppData. It registers as `windows` / `powershell-5.1`. The Local Sidecar integration suite runs on a Windows CI runner.

**Blocked by:** 08 (Sidecar connects by URL and reports its OS and shell)

**Status:** resolved

Spec: [Omarchy Bot app](../spec.md). Architecture: [ADR 0015](../../../docs/adr/0015-omarchy-bot-app-is-the-only-bot-client.md).

- [ ] `local.run` executes PowerShell 5.1 syntax and returns output and exit code
- [ ] Cancel and timeout terminate the command and every descendant
- [ ] Windows credential and key stores are refused
- [ ] Registration reports `windows` and `powershell-5.1`
- [ ] The Sidecar suite, including Windows-only cases, passes on a Windows CI runner

## Comments

Implemented the Windows executor and its cross-platform policy: `windows` LocalExecutor running Windows PowerShell 5.1 in text output mode, assigning each job to a Job Object with kill-on-close before the command is released through stdin, so cancel, timeout, and shutdown terminate the command and every descendant. Registration now accepts `win32` and reports `windows` / `powershell-5.1`; the Windows credential and key-store denylist is case-insensitive, expands real NTFS long paths (blocking short-alias bypass, including missing write destinations), and is enforced for every file action; the shared Linux credential file-action policy leak is fixed. PowerShell failures surface as explicit text errors. Docs, workflow, and tests updated; a `sidecar-conformance` workflow runs Linux/macOS/Windows jobs plus a native compiled binary suite.

This comment supersedes the earlier `needs-info` status and the Pi-conformance blocker recorded here previously; both are retired by the evidence below. The acceptance boxes stay unchecked because no post-fix Windows CI run has been observed green yet. The ticket is resolved at the user's direction on the strength of code, portable-execution, and cross-compilation evidence, with runtime confirmation on a real Windows runner explicitly deferred to the rerun.

Actual CI evidence, authoritative URL: https://github.com/x-metheus/omarchy-bot/actions/runs/40802739289/job/123214404207 at `e1cc138d`. The Ubuntu and macOS jobs passed, including their compiled Sidecar suites. The Windows x64 job reported 12 pass, 5 skip, 3 fail (117 assertions); native compile and the compiled-process suite were skipped there. The three failures and their fixes: (1) first-use progress records contaminated the remembered-output assertion with CLIXML, a capture problem rather than a persistence defect — the bootstrap now sets `$ProgressPreference = 'SilentlyContinue'` before module activity, and framed CLIXML warnings and errors are decoded to readable text; (2) the warning/error case returned exit 0 and raw CLIXML because invocation masks nonterminating errors — status is now captured inside the executed script's final block, and the completion write uses `$script:completion` so a user `$completion` variable cannot redirect it; (3) the successful-application case hit the 25 s timeout because incidental inherited handles held pipes open — each Windows job now captures stdout and stderr in private temporary files and writes a completion marker on normal script return, while an explicit `exit` bypasses the marker and waits for the Job Object's active process count to reach zero via `QueryInformationJobObject`. The bootstrap parses its input and inserts the status trailer into the final execution block, preserving top-level named blocks, parameters, directives, and comments. Regression tests were added for each failure, including executor cases and the production compiled process.

Verification after the fixes: focused portable PowerShell 7.6.9 on Linux plus Sidecar/process suites gave 40 pass, 15 skip, 0 fail (296 assertions, 15.77 s). Production-extracted bootstrap and capture checks covered Unicode output, native and explicit-error exit status, token stripping, truncation, the stdin gate, named blocks, report preservation, and survival of an inherited-writer child; these do not exercise kernel32 or Windows PowerShell 5.1. Full `bun test` gave 834 pass, 26 skip, 0 fail (5,320 assertions, 860 tests / 125 files, 524.29 s); that run preceded the last scope/parser correction, after which the focused proof, `bun run typecheck` (0 errors) and `bun run lint:boundaries:2` (2 pass, 0 fail) passed but the full suite was not rerun. Native Linux `bun build --compile` succeeded and the compiled-process suite gave 5 pass, 2 Windows-only skip, 0 fail (51 assertions). Windows x64 cross-compile succeeded: 698 modules, PE32+ AMD64, 115,743,744 bytes, SHA256 `6436093e6e53352d57cef3c2a492188e288dd44e5be6a80349279481bdd02a2c`. actionlint 1.7.12 and YAML matrix validation exited 0 with no diagnostics. Pi 0.84.4 conformance using the user-supplied private models and settings recipe with `0600` auth passed 11 conformance steps plus steering, including image, screen, and browser, with 25 identity records and 6 sessions and no fallback; the private config, auth, and conformance HOME under `.lane` were deleted and host settings were not changed. A host install was not performed. Standards and spec final reviews are both clean.

Not observed, and why the boxes stay unchecked: PowerShell 5.1 syntax, Unicode, status, named blocks, returns, token, truncation and diagnostics behavior; Job Object assignment, accounting, cancel, timeout, root-exit descendant kill and natural application release; Windows capture cleanup and handle sharing; real NTFS aliases and file policy; native Windows compilation and the whole compiled-process suite including TLS, policy, cancel, and the two new regressions. These require the user to push and rerun the `sidecar-conformance` workflow on `windows-latest`; this ticket makes no claim that such a run has passed.
