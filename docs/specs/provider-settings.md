# Provider Settings

Use a dedicated Settings page in the desktop App. The first release of this feature adds custom OpenAI-compatible providers that use the Responses API. Related decisions are recorded in the [Agent Daemon ADR](../agents/adr/0017-rig-agent-daemon.md) and the [Provider Configuration glossary entry](../../GLOSSARY.md#language).

The published implementation specification is tracked in [GitHub issue #36](https://github.com/x-metheus/omarchy-bot/issues/36).

## Settings page

- Keep **Settings** at the bottom of the App sidebar. Open Settings in the main content area. Selecting a Bot returns to its Conversation. Preserve the selected Bot, unsent chat draft, and draft attachments while Settings is open.
- Put the existing local daemon launch preference in **General**. In **Providers**, show the connected Agent Daemon, its current provider and model, and the saved configurations. Provide actions to add, edit, and set a configuration as current.
- The custom provider form contains a display name, an API Base URL, an authentication choice, and a searchable model selector. Authentication choices are **API Key** and **No authentication**. The Base URL is the API root, for example `https://example.com/v1`. It must be reachable from the connected daemon host. For a remote daemon, loopback refers to that host. Discovery and configuration writes use the existing Settings authorization and HTTP(S) URL validation.

## Model discovery

- The Agent Daemon configures Rig's `OpenAIConfig` with the supplied Base URL and credential. Use `Auth::OptionalBearer` to omit the authorization header for **No authentication**. Use `OpenAI::list_models()` for `GET /models` and `OpenAI::responses(model)` for `POST /responses`. The Responses API is the only completion protocol for custom providers in this feature. [Rig OpenAI client](https://docs.rs/rig-core/0.47.1/rig_core/providers/openai/struct.OpenAI.html) · [Rig authentication source](https://github.com/0xPlaygrounds/rig/blob/v0.47.1/crates/rig-core/src/providers/openai/wire/auth.rs) · [OpenAI migration guide](https://developers.openai.com/api/docs/guides/migrate-to-responses)
- Fetch automatically when the form has a valid Base URL and authentication is ready. A stored API key counts as ready for the saved Base URL. Wait for the user to finish editing before fetching. Apply results only to the connection that requested them. A refresh action requests the current list again.
- Show loading, empty, and error states. Model selection comes from the returned list. Saving requires a selected model from a successful fetch for the current connection. A failed or empty fetch leaves the saved configuration and current model intact. A successful listing makes model IDs available for selection. Actual Responses support is determined by the service when it handles a model request. [Rig model-list wire](https://github.com/0xPlaygrounds/rig/blob/v0.47.1/crates/rig-core/src/providers/openai/wire/modality.rs)

## Save and activate

- A **Provider Configuration** stores a provider and one selected model. The same Agent Daemon can keep multiple configurations. Each custom provider has its own identity, display name, Base URL, authentication choice, and credential. Two configurations may expose the same Model ID.
- The Agent Daemon persists configurations and the current selection in SQLite and uses its existing credential encryption. Paired clients see the same saved configurations for that daemon. Reads return credential presence. Reuse a stored API key only for its saved Base URL. When changing that URL, require a new key or an explicit choice of **No authentication**. Keep existing built-in provider settings and environment bootstrap compatible with the new configuration model. [Current Settings API and persistence contract](../../apps/agent-daemon/README.md#settings-api)
- **Save** stores a configuration. If there is no current model, the first save also makes the configuration current. Saving an inactive configuration while a current model exists leaves the selection intact. **Set as current** activates a saved configuration for all Bots on the daemon. Saving edits to the current configuration applies the update to new Turns. Commit each successful change atomically.
- A Turn keeps the model connection captured at admission. Saving or switching leaves requests already sent in flight. If the upstream service revokes the previous key, it can reject subsequent requests made with that key by an existing Turn. New Turns use the latest committed current configuration.

## Runtime logging

- Use `tracing` with one `tracing-subscriber` per Rust process. Initialize Tauri logging before native runtime creation so startup failures and early panics are recorded. Keep `omarchy-bot.log` in the existing App log directory, including the native smoke profile override. Emit lifecycle events to stderr as well. [Current Tauri startup](../../apps/omarchy-bot/src-tauri/src/main.rs)
- The Agent Daemon initializes logging before opening its database and records startup failures through that subscriber. Standalone instances write to stderr for the terminal or service manager. The App passes its log directory to a managed Daemon, which owns its own `agent-daemon.log` writer and rotation. Preserve the Daemon's `LISTENING` line on stdout for readiness consumers. [Current Daemon startup](../../apps/agent-daemon/src/main.rs)
- Use `rolling-file` for on-disk logs. Rotate each stream at 5 MiB and retain three archives plus the active file. Keep records intact at the rollover boundary. Keep log files in user-private storage, serialize rotation with one writer per file set, and use stderr if a file writer is unavailable. Use synchronous, unbuffered writes for these low-volume diagnostics so lifecycle records are written before restart or exit. [Size-based rotation and retention](https://docs.rs/rolling-file/0.2.0/rolling_file/)
- Default to `INFO`. Allow `RUST_LOG` to adjust first-party targets within a fixed allowlist. Log lifecycle events and sanitized Provider operations using fields such as duration, HTTP status, model count, and a stable error code. Exclude API keys, tokens, authorization headers, Conversation content, and raw provider request and response bodies at all levels. Keep Bevy's `LogPlugin` disabled because Rig diagnostics can include upstream response bodies. [Current Rig log policy](../../apps/agent-daemon/src/agent.rs)

## Acceptance cases

1. Open Settings from a Bot with an unsent draft and return to the same Conversation with the draft intact. The local daemon launch preference remains available under General.
2. Enter a reachable Base URL and API key. Confirm the daemon automatically requests `/models`, shows the returned IDs, and sends the chosen ID to `/responses` when starting a Turn. Repeat against a service that accepts anonymous requests and verify the authorization header is omitted.
3. Cause an empty response or a model-list failure and confirm the user sees the corresponding state and can refresh. Enter another Base URL while the first fetch is in flight and confirm the old results cannot be selected for the new URL.
4. Save two configurations, restart the daemon, then connect a paired client. Both configurations and the active model are restored. Saving the second while the first is current leaves the first current until **Set as current** is used.
5. Edit the current configuration while a Turn is running. An already-sent request remains in flight, and a newly admitted Turn uses the updated configuration. An unsuccessful save preserves the previously committed settings.
6. In the desktop App, start the managed Daemon and confirm that the native and daemon logs reach their own files. Trigger a daemon startup failure and confirm that its log records the failure. Run a standalone daemon and confirm that diagnostics go to stderr while `LISTENING` remains on stdout.
7. Exercise both file streams with a small rotation threshold. Verify that each retains an active file and at most three archives. Check that fixture secrets and upstream response bodies stay out of logs with `RUST_LOG=trace`.
