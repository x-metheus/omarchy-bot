# Drive the pack browser over a private CDP pipe

Status: accepted on 2026-10-28. Extends [Computer ADR 0010](0010-daemon-owns-bot-computer-input.md) and [Computer ADR 0011](0011-bundle-one-sway-bot-computer.md); it does not change the shared Bot Computer, routed Screens, serialized seat, or the pack default. Implementation is tracked by [ticket 17b](../../../../.scratch/standalone-linux-service/issues/17b-browser-agent-tools.md) under [the standalone Linux Service specification](../../../../.scratch/standalone-linux-service/spec.md); its anti-bot neutrality criterion is currently unmet (see Consequences).

Agents could already see a Bot Screen as pixels and act through raw input. That is enough to recognize a page and not enough to operate one reliably: element identities, names, values, and states are invisible, and a typed value or a click may land on the wrong thing after a reflow. The pack browser is the one browser the Service owns, with a known version and a known launch flag set, so it can also expose its structure without relying on host policy.

The daemon launches that pack browser with `--remote-debugging-pipe` and drives it over the two extra child descriptors Chromium defines: commands on fd 3, replies on fd 4, NUL-delimited JSON. No TCP debugging endpoint is opened, so nothing on the host or network can attach to a Bot's browser. One in-process runtime adopts the pipe of the live pack browser and scopes targets and element authority to the routed browser windows of each Screen, so a Bot can neither see nor act on another Screen's tabs. A Screen may own several browser windows; `tabs` spans all of them. When the `browser` tool launches the browser itself, it registers the new target and its routed Sway window directly. Otherwise a window is eligible only when Sway reports the same process id that the private pipe's `SystemInfo.getProcessInfo` identifies as its browser; ownership then needs a unique title and matching window dimensions and is pinned by Chromium and Sway window ids. Ambiguous matches are refused rather than guessed. If Chromium cannot report a target's window, the target is rechecked: a target that is still live rejects ownership instead of disappearing from the comparison and letting an equal-title window on another Screen be adopted, while a target that has just been destroyed is ignored as a race with its own teardown. The selected tab is read from each candidate tab's isolated-world `document.visibilityState`, and an unclear selection fails closed instead of picking one. Wayland Chromium reports global window `left`/`top` as zero, so CDP coordinates cannot correlate a window with an output; routing comes from Sway.

Agents get a `browser` tool beside `computer`: `snapshot` returns the accessibility tree with refs, roles, names, values, and states, and `click`, `type`, and `select` accept a ref from the latest snapshot. An Element Ref is valid only until the next snapshot, navigation, tab change, or document replacement; a stale ref fails and tells the Agent to take a new snapshot rather than guessing a selector. `navigate`, `back`, `read_text`, `tabs`, and `wait_for` cover page, history, text, tab, and waiting needs, with byte caps so a large page cannot flood the Turn. `wait_for` tests a condition against the full page text without returning it, so its text search is not limited by the `read_text` cap; `read_text` and `snapshot` stay capped, and a worker result states when truncation omitted content.

Structure first, pixels as fallback. The `browser` tool is the preferred interface for ordinary pages; screenshots and raw input remain available for canvases, custom widgets, and anything the accessibility tree does not describe. `click`, `type`, and `select` are real input at the element's on-screen position through the existing daemon input path and its serialized seat: the element is scrolled into view, its box is mapped from inner viewport coordinates (including scrollbar gutters) to the routed window, and the pointer or key event travels through the same helper as a `computer` action. They never call page `.click()` or assign a value.

Launching stays neutral to anti-bot checks by omission: the pack window uses the same non-automation flags as `open_url`, page targets never receive `Runtime.enable`, and page scripts run only in isolated worlds created by the Service. No startup script is registered on page documents and no main-world evaluation is performed, so a page cannot observe Service script through its own globals. This is not sufficient by itself: the pinned Chrome for Testing build sets `navigator.webdriver` to true for any launch with `--remote-debugging-pipe` before a client attaches, because Chromium hardcodes its automation-controlled feature for that switch. The Service does not spoof the value, patch the flag, or override Chromium features to hide it. The neutrality criterion therefore remains unmet and open in the ticket; the pipe is still preferred over a TCP endpoint because the remaining signal comes from the switch Chromium requires for structure, not from the transport.

Every browser action goes through the Computer Broker under the same per-Screen serialization and Takeover rules as `computer`. A user Takeover holds a pending browser call exactly as it holds a computer call, and the call resolves with a fresh snapshot instead of a stale screenshot when the user selects “I'm done.” An Agent that meets a CAPTCHA, an anti-bot challenge, a login, or a payment step calls `request_takeover` with a short reason. The call first confirms the Screen runtime is ready and refuses a host-browser opt-in with the same actionable error, before anything is held; it does not require an already-open browser window. The invocation then stays pending, Web Control and the Computer Surface show the reason, and the Agent resumes from a fresh snapshot after the user is done. A Bot never tries to solve or bypass a challenge.

The pack browser is launched as a directly owned session child rather than through the transient-unit path used for ordinary applications. `systemd-run --pipe` cannot forward the extra descriptors the CDP pipe needs, so `ApplicationUnits` does not apply to that launch; existing tracked-child teardown still stops that browser's process tree with the Bot Computer. The shared Bot Computer browser profile of Computer ADR 0009 is unchanged, so sign-ins carry across Screens.

The `OMARCHY_BOT_BROWSER=host` opt-in remains a `computer`-only path. A host browser has no Service-owned pipe, an unknown version and flag set, and may be Firefox, which removed CDP. `browser` therefore fails with an actionable error there instead of silently switching browsers; an opted-in host that falls back to the pack uses the pipe normally.

## Considered Options

- **Add a browser-automation dependency (Playwright, Puppeteer, or a CDP client library)**: rejected; each brings its own browser download or launch policy, and the Service already owns the exact pack binary, profile, and launch flags. A small NUL-framed JSON client is the whole requirement.
- **A TCP `--remote-debugging-port` endpoint**: rejected; it exposes the Bot's browser to anything that can reach the port, needs an extra listener and cleanup, and gains nothing over the inherited pipe.
- **Drive clicks and typing with page script (`.click()`, value assignment)**: rejected as the primary path; it bypasses the serialized input seat and Takeover, and pages can detect or override it. Real input keeps one arbitration model for `computer` and `browser`.
- **A headless agent browser such as Lightpanda as the default**: rejected for the Bot Screen; the user must be able to watch and take over the same window. It remains a possible separate background tool.
- **WebDriver BiDi**: rejected; the pack is Chromium, Firefox is out of scope, and BiDi would require a different driver and transport for no additional capability here.
- **Treat challenges as an Agent problem**: rejected; the Service does not ship stealth or bypass behavior, and a person is both more reliable and the correct authority for a login or payment.

## Consequences

- The `browser` tool contract lives in `packages/agent-contract` beside `computer-tool.ts` and is exposed by real (Pi) and scripted workers.
- Snapshot text is capped (about 16 KiB / 300 nodes) and `read_text` about 8 KiB; truncation is reported so an Agent can narrow its snapshot rather than assume completeness.
- Screen ownership is registered directly by an auto-launch and otherwise inferred only for windows whose Sway process id matches the pipe's browser process, using a unique title and matching dimensions, then pinned by window identity; ambiguous or foreign windows are refused rather than guessed. The selected tab comes from isolated-world `document.visibilityState` and also fails closed, and Wayland's zero CDP window offset means output position is never used for correlation.
- Chromium's singleton behavior means a repeated `open_url` may hand off to the existing browser process; the adopted runtime stays attached while that process lives.
- Sites can still challenge or block the Bot. IP reputation, datacenter or VPS addresses, and site policy are often the deciding factor and are outside the Service's control, and `navigator.webdriver` remains true for the pipe launch until a neutral control channel exists.
- Losing the pipe to a daemon restart has no reconnect path; the browser must be relaunched and the failure is reported rather than masked.
- The host-browser opt-in deliberately has no browser tool; users who need Agent browser control use the pack.
